# Measurement data and instruments in Particula

Design review, 28 November 2026. Reviewed the public main revisions of [particula-dev-data, 4e56f7d](https://github.com/Gorkowski/particula-dev-data/tree/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8) and [Particula, 3c364f5](https://github.com/uncscode/particula/tree/3c364f574b3fc2ce6da970aaa5571be85cfda370). The latter declares version 0.3.6. The numerical checks below used files at the donor revision. The instrument-model findings are source reviews.

The [streaming import plan](measurement-import/streaming.md), [implementation map](#implementation-map), [campaign features](#campaign-features-and-acceptance-cases), [configuration contract](#a-configuration-a-person-or-an-llm-can-validate), [import examples](#instrument-import-examples), [two-PR implementation split](#two-implementation-pull-requests), [delivery sequence](#delivery-sequence-and-evidence), and [complete beta file index](measurement-import/beta-index.md) accompany this review.

## Decision

Adopt the instrument format knowledge, calibration workflows, and representative cases. Use **Polars as the tabular engine for an optional measurement-data install**. Return the actual Polars table so users can select, join, aggregate, and export using the library's own API. A small Particula result should carry the table alongside its field definitions, provenance, and parse report. Store fixed-grid spectra and other fixed-shape measurements as Polars Array columns, one observation per row. Expose a NumPy array for physical calculations. Instrument forward models should take physical arrays or native aerosol state and return named physical quantities with explicit axes. This keeps instrument calculations available with the existing simulation dependencies.

There are two separate reasons for these choices. On clean instrument exports, Polars was faster in the local comparison below. On damaged files, both engines need a reader that understands what a valid observation looks like. A reusable reader and its independently checked outputs are the highest-value contributions here.

### Reuse the existing parser and change the output

Port the settings-driven text loader and its focused tests into `particula.data`. The current scalar formatter already returns timestamps and a numeric matrix. The sizer formatter returns those plus the channel headings. The existing interface creates or appends to a `Stream` afterwards. At that boundary, construct a Polars frame with an explicit time column and named, typed channels. A sizer reader can also expose its existing scan-by-channel array and diameter coordinate directly for numerical work. Keep a generic path that accepts a user's existing supported settings dictionary. Named particle-counter and mobility-sizer readers can supply profiles to that same parser. [Formatter outputs](https://github.com/Gorkowski/particula-dev-data/blob/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8/particula_beta/data/loader.py#L433-L613) · [Stream assembly](https://github.com/Gorkowski/particula-dev-data/blob/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8/particula_beta/data/loader_interface.py#L287-L325)

Make two checks during that port. First, read a clean file with the same settings in both implementations and compare timestamps, channel order, values and missing entries. Second, capture source line numbers before filtering and preserve raw status tokens before numeric coercion. Those details cannot be recovered by changing the return type afterwards. Compare the damaged CPC file against the independently reconstructed records. The timing trial below measured direct dataframe CSV reads; profile the reused parser end to end before optimizing it.

### Spectra and higher-dimensional measurements

One scan can contain a scalar count rate, a vector of diameter bins, or a matrix of diameter bins by wavelength. A Polars frame can hold all three alongside timestamp, scan ID and quality flags. Use a fixed-shape `Array` column for each vector or matrix. Keep dimension names, coordinate values or bin edges, units, and coordinate basis with the measurement. Use a grid ID to reference shared coordinates. Two scans with equal array shape can still have different physical grids. For genuinely variable-length event lists, a `List` of records can keep each event's coordinate and signal together.

For example, one row of an optical instrument can hold a 203 × 3 signal with axes diameter and wavelength. Reading that column into NumPy gives shape (scans, 203, 3). In a local Polars 2.2.0 check, a five-row table containing a four-element spectrum and a 3 × 4 signal on every row preserved both array schemas and all values when written to Parquet and read back with Polars. This check covered values and shapes; the measurement reader must also serialize and verify the coordinate definitions. An xarray view supplies named axes for scientific selection and integration. When the routine task is reading small spatial or spectral slices of a much larger cube, prefer an xarray dataset backed by chunked Zarr or NetCDF, with scan metadata in Polars if needed. [Polars lists and arrays](https://docs.pola.rs/user-guide/expressions/lists-and-arrays/) · [xarray coordinates and dimensions](https://docs.xarray.dev/en/stable/user-guide/data-structures.html)

### Explicit Warp GPU processing

Select scans and channels in Polars, group compatible grids, and upload each fixed-shape numeric batch explicitly with `wp.array(host, dtype=..., device="cuda:0")`. A one-chunk, null-free Array column of a compatible type can provide a CPU NumPy view via `to_numpy(allow_copy=False)`. The host-to-device upload still copies data. Where packing or casting is needed, perform it once per batch. Pass a validity mask when a kernel needs missing channels and upload physical coordinates when the calculation uses them. Keep scan IDs and source metadata with the host batch. Retain intermediate Warp arrays on the GPU across kernels and attach downloaded results to the corresponding scan IDs. Existing Particula transfer helpers serve native simulation state; a measurement can go straight to a Warp array.

Verified on an NVIDIA GeForce RTX 5060 with Polars 2.2.0 and Warp 1.11.1. A five-scan frame held a 3 × 4 float64 signal per scan. Filtering to scans 0, 2 and 4 produced a (3, 3, 4) NumPy view without an additional copy at export. A CUDA kernel doubled each value. Reading the result back into a new Polars Array column preserved all three IDs, both physical axes and every expected value exactly. This tested dense fixed-grid data; variable-length events and nullable input require their own transfer policy. [Polars NumPy export](https://docs.pola.rs/api/python/stable/reference/series/api/polars.Series.to_numpy.html) · [Warp arrays and devices](https://nvidia.github.io/warp/v1.17/user_guide/runtime.html)

### An independent numerical check

For the July 7 SMPS export, I summed the 203 reported number-per-decade values in each scan and divided by the declared 128 channels/decade. The first scan yields 2168.99816 cm⁻³ against the instrument's 2169.0 cm⁻³. Across all 2,854 scans the maximum absolute relative difference was 4.97 × 10⁻⁶. This checks the reader's column selection, interpretation of number weighting, and logarithmic width against the vendor's printed total. It does not establish instrument calibration or the correct rule for a different export. Preserve the unrounded grid spacing where specified. Independently deriving widths from rounded text labels changes the calculation. ### Two model limitations that affect the order of work

The beta CCNC wrapper validates κ and then leaves it unused. The underlying selection uses the last rounded number of slots. When that rounded number is zero, Python's slice beginning at minus zero returns the entire population. Sorting and counting slots also loses the represented number when particle weights differ. A port should test zero activated particles, unequal weights, partial selection at the cutoff, per-box volume, and radius versus detector diameter. Keep the measured-total-conditioned histogram available as a distinct observable if a study needs it. [CCNC calculation](https://github.com/Gorkowski/particula-dev-data/blob/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8/particula_beta/instruments/ccnc.py#L251-L280) · [CCNC wrapper](https://github.com/Gorkowski/particula-dev-data/blob/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8/particula_beta/instruments/ccnc/simulator.py#L133-L164)

The optical simulator accepts multiple wavelengths and evaluates only the first. Its bulk-to-aerosol conversion method returns the object it received. Start with an optical response that takes a validated native population and returns the signal at each requested wavelength, with the collection geometry explicit. Particula's Pallas study is a second application that already distinguishes the true droplet diameter, detection probability and reported size. Its field mismatch also illustrates why a numerical response check and agreement with field data are separate claims. [Beta optical simulator](https://github.com/Gorkowski/particula-dev-data/blob/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8/particula_beta/instruments/optical/simulator.py#L390-L429) · [Native optics](../particula/optics/__init__.py) · [Pallas probe study](../docs/studies/literature/pallas-cloud-probes/index.md)

## Implementation map

The implementation base is [upstream `0fa70c4964`](https://github.com/uncscode/particula/commit/0fa70c496438a8eb9665486f1331a4f61ab2c381), which declares Particula 0.4.0. Its native particle population is extensive. Keep measured number concentration and number per decade in their declared units; conversions to native counts require the represented air volume and the distribution measure. Add an unequal-volume control when comparing simulated and instrument spectra. [Native population contract](../docs/guide/data-model/index.md) The accompanying [beta source index](measurement-import/beta-index.md) maps all 81 runtime/package files to a disposition and links all 90 additional test and fixture files in the donor package. The schema and profiles below are design fixtures. The Python entry points in the examples describe the intended API.

## General and specific instruments with prescribed processing

A user can define an instrument in their own project by supplying a reader profile, a deployment and Python operations for calibration or signal processing. Built-in `ParticleCounter` and `MobilitySizer` instruments use that same interface and expose typed conveniences. Instruments own the processing definitions; a measurement process takes one or more named inputs and creates a new value-added measurement with all parent references. `execute()` and ordered composition follow Particula's simulation vocabulary; the measurement executor handles observed time, QC, calibration and output lineage. The [instrument extension and runnable design](measurement-import/instrument-processes.md) includes a custom flow meter, a built-in particle counter, equivalent Python and declarative processing, and failure and batch-boundary checks.

Use **strategies** for file decoding and processing algorithms, a **registry-backed factory** for selecting those implementations from configuration, and **builders** for instruments with genuinely multi-step setup. The first particle counter and mobility sizer share a delimited reader and use validated profiles directly. The [design decision and acceptance checks](measurement-import/instrument-processes.md#where-strategies-builders-and-factories-belong) map these choices to the existing condensation and coagulation factories.

### Built-in naming

Use the measured quantity or operating principle for public types, reader names and operation identifiers. `ParticleCounter` covers number-counting instruments; the 3010 profile records condensation particle counting as its detection principle. `MobilitySizer` covers electrical-mobility sizing; the AIM profile describes the vendor export. `AerodynamicSizer` identifies instruments reporting aerodynamic diameter. The cloud activation instrument has its own descriptive name, `CloudCondensationNucleiCounter`. Keep vendor labels, model numbers and export versions in profiles and provenance so users can locate the right parser. Use the actual product, such as `ParticleCountRate` or `MobilityNumberSpectrum`, to decide which operations apply.

## Instrument types and operation compatibility

Give the named readers concrete return types. For the first fixtures, `read_particle_counter()` with the 3010 logger profile returns a `ParticleCountRate` and `read_mobility_sizer()` with the AIM number profile returns a `MobilityNumberSpectrum`. Each is a validated view of a measurement and shares its Polars buffers, grid references, QC and provenance. The base `Measurement` remains available for custom files. The profile's optional `instrument_family` records the source family. A CPC export containing concentration and a CPC export containing count rate produce different measurement products even when their instrument metadata agree. Add product types as real readers and operations need them. [Python type annotations](https://docs.python.org/3/library/typing.html)

| Proposed operation | Signature or requirement | Check before applying |
| --- | --- | --- |
| Select a time window | Any measurement with a compatible clock | Preserve scan IDs, grid references and QC. Reject incompatible time bases. |
| Derive a sampled-air number concentration | CPC count rate in counts/s and positive sample flow in volume/time | A scalar flow has declared units and provenance. A flow series also needs matching time support and valid QC. Record the flow and conversion in the derived product. Detection efficiency and coincidence corrections require separate evidence. |
| Integrate a number spectrum | Any compatible number-per-decade spectrum with known log-bin widths | Check axis, measure, width convention and coverage. A scalar CPC rate cannot satisfy this input. A mobility-specific comparison additionally requires the mobility diameter basis. |

Expose operation signatures to Python tooling and an `available_operations()` query to configuration-driven callers. Each operation should declare its required quantities, units, axes, additional inputs and output product once. Use those same declarations for discovery and runtime checks. For the July CPC file, discovery can report that deriving concentration needs `sample_flow`; a caller can supply it explicitly. A family string or a Python cast cannot validate physical data. A generic `read_measurement()` can be narrowed via a validating constructor when a caller needs the concrete product. An unknown family can still use operations whose scientific requirements it meets.

Allow direct Polars access. A raw projection, join or arbitrary expression yields an ordinary frame; to reattach a typed view, validate the transformed columns, their units, row identities and grid linkage against the manifest. Operations provided by Particula can preserve a type when their contracts guarantee it. On Parquet reload, reconstruct the validated view from the versioned product definition and manifest. Derived quantities should record the operation, source fields, parameters and units. For streaming partitions, validate metadata at open and check batch-dependent values while reading.

Implement acceptance cases alongside the CPC and SMPS readers: a type checker rejects a CPC rate where a spectrum is required; a generic caller gets an actionable runtime diagnostic for the same request; discovery requests flow before offering the CPC conversion as runnable; filtering retains scan provenance; deleting the rate column prevents reconstruction of a count-rate view; a valid Parquet round trip restores the same operations.

## Multiple instruments in one collection

Implement `MeasurementCollection` in `particula.data` as a mapping from run-specific names to validated measurement products. Keys such as `inlet_counter` and `outlet_counter` can identify two instances of the same instrument family. Each entry keeps its clock, coordinates, QC, source identity and Polars frame or lazy scan. Constructing a collection keeps references to those entries. It incurs no join and imposes no common sampling frequency. The beta lake already supports named lookup and applies averaging to each stream; carry both behaviors forward. [Beta lake averaging](https://github.com/Gorkowski/particula-dev-data/blob/4e56f7da0d29b6c5cb08d8dcc36cf40c990ef8b8/particula_beta/data/lake_stats.py)

```python
campaign = MeasurementCollection({"inlet_counter": counter, "mobility_sizer": sizer})
hour = campaign.select_time(start, stop)
minute = hour.average(
    every="1m", origin=start, weighting="sample",
    fields={"inlet_counter": ["count_rate"], "mobility_sizer": ["total_number"]},
)
comparison = minute.align_windows(how="grid")
```

This proposed API returns a new collection after selection or averaging. Every member uses the same explicit window origin, clock, and half-open interval convention. Each member aggregates its own observations first. The explicit alignment then yields one row per requested window, with instrument-qualified fields and separate valid sample counts. An empty window has count zero and a null mean. Return valid exposure or coverage when it can be determined. Sample counts alone do not establish coverage. Record aggregation, weighting, window and parent sources on derived products. Preserve the original collection.

Use sample weighting for a mean of reported samples; offer duration weighting for interval means with documented support and explicit handling of partial overlaps. Sum actual counts over exposure, average spectra per channel on compatible grids, and aggregate status flags according to their definitions. Resolve incompatible or unknown clocks before cross-instrument alignment. Validate requested fields, units and grids per member, and name any unsupported operation before execution. For raw nearest-time matching require a tolerance and retain the time offset. Keep the sequence lazy for Parquet-backed members and permit writing the comparison directly to disk.

A fixture check used the July 10 CPC and SMPS exports between 12:00 and 13:00 UTC, following the donor SMPS timezone setting. Polars independently grouped 1,203 CPC readings and 40 SMPS scans, then joined both summaries to a 60-row minute grid. CPC had data in every minute; SMPS had data in 40. All nonempty sample means agreed with independent NumPy calculations and the remaining 20 SMPS means were null. This checks timestamp-window assignment; for this check SMPS scans were assigned by their reported start time. An exposure-weighted comparison would require scan intervals. Include these cases plus two instances of the same instrument, a grid change and a clock-origin mismatch in the implementation tests. [Polars window grouping](https://docs.pola.rs/api/python/stable/reference/dataframe/api/polars.DataFrame.group_by_dynamic.html)

## A configuration a person or an LLM can validate

The [draft JSON Schema](measurement-import/profile.schema.json) describes field meanings, required keys, defaults where supported, column selectors, timestamp formats, units, supported quantity definitions and repair policies. The same schema accepts the [CPC YAML](measurement-import/cpc-3010.yaml), [equivalent CPC JSON](measurement-import/cpc-3010.json) and [SMPS JSON](measurement-import/smps-aim.json). Its first two instrument profiles cover scalar records and a 1D spectrum per scan. Matrix-valued variables, event lists, APS threshold channels and NetCDF require subsequent schema extensions, fixtures and readers.

1. **Decode one portable data model.** Accept JSON or plain YAML mappings, lists and JSON-compatible scalar values. Reject duplicate keys, custom YAML tags, cycles, nonfinite numeric literals and unsupported major versions. Resolve the declared schema against the installed schema catalog offline. Validate closed object keys. Canonicalize the decoded profile for hashing so equivalent YAML and JSON yield the same identity.
2. **Check the measurement definition.** Require a stable name, human-readable description, quantity, dtype and source/output unit for numeric measurements. Use a controlled unit vocabulary plus a separate quantity and measure identifier. Verify compatible dimensions and use affine conversion for temperatures. Counts/s to concentration requires flow and a documented model. A density per decade and integrated density share formal units but have different meanings. Reject a request to transform one into the other through a unit factor alone. Validate unique output names and reserved metadata names, IANA zones, precision, and ordered, consistent axes.
3. **Bind against a real file.** An inspection call reports encoding, header candidates, raw unit strings, preamble values, candidate axes, clock examples and ambiguous mappings with source locations. Match configured columns exactly; ambiguous or missing headers and unsupported weighting yield structured errors. Record the original spelling, normalized units, axis basis, source of the timezone, applied corrections, parser version, source digest, canonical profile digest and any overrides in the result. Preserve instrument quality status alongside numeric values.
4. **Return actionable diagnostics.** Proposed fields are `severity`, stable `code`, `profile_path` (JSON Pointer), `source_record` or line span if available, `observed`, `expected`, and a plain-language explanation. For example, `unit_incompatible` at `/fields/0/output_unit` should identify count rate and the permitted units. Missing evidence such as the site clock zone should be reported as unresolved. A model can suggest a profile, inspect the exact failing field, revise and validate before importing the full file.
5. **Extend under a version.** Publish shape and quantity definitions with examples alongside the schema. A later matrix profile should declare its ordered dimension names, each coordinate's source/unit/basis, source layout, missing masks and axis cardinality. Test a source that changes grids without changing shape. An unsupported profile version should identify which versions the installed reader recognizes.
