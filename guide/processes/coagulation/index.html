      Coagulation Strategy System

      For the supported CUDA configuration of this runnable, use prepared GPU simulations. The CPU and direct-kernel contracts below retain their own, sometimes broader, capabilities.

      Complete direct-process context

      Section titled “Complete direct-process context”

      The direct coagulation call is part of the illustrative explicit-transfer sequence, with direct-process validation evidence and a example regression. Persistent RNG remains caller-owned; the example is not a backend selector, scheduler, Runnable, resident loop, or CPU fallback.

      Strategy-based coagulation kernels with unified builders, factory selection, runnable integration, and particle-resolved support.

      Overview

      Section titled “Overview”

      The coagulation strategy system lets you model particle collisions using the same object-oriented patterns as condensation and wall loss. Instead of calling standalone kernel functions, you work with strategy objects that operate on native ParticleData, support multiple distribution types, and expose a consistent kernel / rate / step interface. Strategies cover Brownian motion, electrostatic enhancement, turbulence (shear and DNS), gravitational sedimentation, and user-defined combinations.

      This feature is built around user-facing APIs exposed via particula.dynamics:

      • CoagulationStrategyABC – abstract base class defining kernel, gain/loss/net rate, and step for discrete, continuous, or particle-resolved distributions.
      • BrownianCoagulationStrategy, ChargedCoagulationStrategy, TurbulentShearCoagulationStrategy, TurbulentDNSCoagulationStrategy, SedimentationCoagulationStrategy – concrete physical models.
      • CombineCoagulationStrategy – sums multiple kernels of the same distribution type for combined physics.
      • Builders for each strategy plus mixins for distribution type, turbulent dissipation, fluid density, and charged-kernel validation.
      • CoagulationFactory – factory for selecting a coagulation strategy by name with builder defaults.
      • Coagulation runnable – delegates to a coagulation strategy, splits time_step across sub_steps, and composes with other runnables using the | operator.

      The Coagulation runnable requires a native Aerosol holding ParticleData, GasData and EnvironmentData. Each equal substep reads the current held population and environment. Strategies must return the same particle container; the runnable rejects replacement results. Gas state remains held independently. The runnable’s rate forwards the strategy’s native rate without changing its population measure. Non-native aggregates reject before strategy dispatch.

      Native kernel and rate contract (v0.3.0)

      Section titled “Native kernel and rate contract (v0.3.0)”

      The six concrete CPU strategy families accept explicitly tagged ParticleData for kernel evaluation: Brownian, charged, sedimentation, turbulent shear, turbulent DNS and compatible combinations. Configuration stays on strategies. Every native entry revalidates representation and physical state, requires one box and matching distribution_type, and checks scalar temperature/pressure. Mutated mechanism controls and combined child distributions are checked again. Non-native objects and untagged populations reject at kernel, gain/loss/net-rate and step boundaries; distribution meaning is never inferred. Combined kernels validate the full population once, evaluate child material laws internally, and restore zero interaction rows and columns for empty slots. This also applies to nested combinations; private material storage is not a supported population-execution input.

      Kernel values have units m³/s and use per-particle material mass, geometry and charge. They do not multiply physical mass by population count. Zero-mass, zero-count slots retain zero rows/columns in the original slot layout; occupied zero-mass particles reject. Existing CPU sedimentation and DNS retain their arithmetic mean of per-particle mass divided by additive material volume. DNS retains its existing ambient-pressure convention; this migration does not change its law.

      Native quantity Interpretation
      Resolved concentration Raw counts; density is N/V for positive physical volume
      Discrete PMF concentration Bin number density, m⁻³; volume must be exactly 1 m³
      Radius PDF concentration dn/dr, m⁻⁴; integrate on explicit increasing radius_grid, at volume 1 m³
      Discrete gain/loss/net rate Number-density change, m⁻³ s⁻¹
      Radius-PDF gain/loss/net rate Radius-density change, m⁻⁴ s⁻¹
      Friction factor kg/s

      PDF quadrature uses the declared radius coordinate; physical kernel radii are still derived from material mass and density. PMF gain uses its existing conversion to PDF on physical radii. The existing cubic gain interpolation requires at least four increasing positive nodes for a nonzero population; shared container metadata does not supply a lower-order alternative. Zero-work rates remain zero. Supplied pair kernels must be real, finite, nonnegative square matrices matching the population width.

      Gain/loss/net-rate APIs remain discrete/PDF operations. Native resolved kernel support does not introduce deterministic resolved rate APIs. The examples below use native state. Independent native fixtures are in particula/dynamics/coagulation/coagulation_strategy/tests/native_rates_test.py.

      Native CPU stepping and conservation

      Section titled “Native CPU stepping and conservation”

      step requires explicitly tagged ParticleData, including on zero-duration calls. Non-native objects and untagged populations reject before numerical dispatch; the method never infers a distribution type. It preserves the input container and its arrays. It validates representation, writable/nonoverlapping destinations, environment and current process controls before publishing a staged update. Rejected numerical proposals leave caller arrays unchanged. Density, volume and the explicit PDF radius grid are protected. These direct strategy methods remain single-box. The Coagulation runnable stages and iterates all boxes, with explicit CPUExecutionContext required for stochastic multi-box execution; see batched CPU execution.

      Discrete/PDF stepping preserves the existing explicit number gain/loss update on a fixed composition grid. It writes concentration only; per-bin species masses and charge remain unchanged. Negative or nonfinite proposed concentrations reject before publication, without clipping.

      Intended use: this fixed-composition PMF/PDF method is suited to particles with uniform composition across radius, or to a population represented as a single effective material with a prescribed effective density. It is generally not appropriate for tracking composition that varies with radius. An effective density is a bulk material approximation, not a replacement for transporting individual species between bins. Uniform composition does not remove the method’s finite-domain and discretization errors.

      Use particle_resolved when species composition varies with radius or when tracking more complex interactions that depend on individual particles’ composition, size, and charge. It retains per-particle species masses as particles evolve and merge. See the native scientific process guide for supported process calls and constraints, including equal positive active counts for resolved coagulation.

      Known limitation: gained particles inherit the destination bin’s fixed composition rather than the combined donor composition. With composition varying across particle size, this method does not generally conserve each species or weighted charge. Refining the radius grid or reducing the timestep does not resolve that composition error, even when total-mass error converges. V0.3.0 deliberately preserves this method; conservative species/charge transport is deferred and is not part of the supported density-step contract.

      For an illustrative two-species, equal-density (1000 kg/m^3), constant-kernel (1e-15 m^3/s) lognormal case, the PDF species defects at 1024 radius nodes are approximately +7.79% and -12.20% of gross transferred species mass, while total-mass error converges. The corresponding PMF defects are +7.43% and -12.49%. These are fixture-specific characterization results, not universal error bounds or percentages of the starting inventory. The fixture spans 1e-9 to 1e-6 m, has geometric mean 1e-7 m, log standard deviation .35 and number density 1e10 m^-3; its first species fraction is clip(.5 + .3*log(r/1e-7), .05, .95). The independent refinement regression retains both the nonzero species defects and the decreasing total-mass error.

      Resolved stepping uses the existing binned/direct selector with equal positive active counts within the box. Unequal active weights reject before drawing; this selector’s merge cannot conserve them. Collision scheduling includes common_count * time_step / volume. Temporary kernel bins carry summed counts and count-weighted material means at the original physical volume; authoritative merges use original slot material and charge. Inactive slots do not participate. The step stages per-species mass, count and charge, preserving weighted species and charge inventories. Selection consumes the strategy’s existing RNG; rejection after draws does not promise RNG rollback or cross-backend seeded equality.

      Key Benefits

      Section titled “Key Benefits”
      • Consistent dynamics workflow: Same strategy-based API (kernel, rate, step, distribution_type) and runnable integration as condensation and wall loss.
      • Builder/factory parity with validation: Fluent builders enforce distribution type, turbulent parameters, fluid density, and charged kernel strategy selection with optional unit conversion.
      • Coverage of major coagulation regimes: Brownian, charged/electrostatic, turbulent shear, turbulent DNS, and sedimentation kernels plus additive combinations.
      • Distribution-type flexibility: Works with “discrete”, “continuous_pdf”, and “particle_resolved” modes so you can reuse existing particle builders.
      • Pipeline ready: Coagulation runnable uses sub_steps, rejects negative native density proposals, and chains with other runnables via | for end-to-end simulations.

      Who It’s For

      Section titled “Who It’s For”

      This feature is designed for:

      • Chamber and box-model users: Running time-dependent simulations where coagulation competes with condensation, wall loss, dilution, or emissions.
      • Particle-resolved modelers: Requiring discrete collision pairs, kernel radius binning, and stochastic pair selection.
      • Turbulence and charged-aerosol researchers: Exploring electrostatic enhancement or turbulence-driven collision rates without re-implementing kernels.
      • Model developers: Extending with new kernels while reusing validation, distribution handling, and runnable plumbing.

      Best Practices

      Section titled “Best Practices”
      1. Match distribution type to particle builder: Keep distribution_type consistent with how native ParticleData was constructed to avoid unintended kernel application.
      2. Use builders/factory for validation: Let builders enforce turbulence units, fluid density, and charged-kernel selection; avoid manual instantiation when sharing configurations.
      3. Start with smaller time_step and use sub_steps: Especially for particle-resolved or highly turbulent cases to reduce overshoot in collisions.
      4. Combine kernels deliberately: Use CombineCoagulationStrategy when you need additive physics (e.g., Brownian + turbulent shear); ensure all strategies share the same distribution type.
      5. Keep parameters physical: Validate dissipation rates, Reynolds lambda, and relative velocities against your experiment or CFD results before running long simulations.

      Limitations

      Section titled “Limitations”
      • Dimensionless kernels are not implemented for combined, turbulent, or sedimentation strategies; use dimensional forms via kernel.
      • All strategies in CombineCoagulationStrategy must share the same distribution_type.
      • No built-in high-level orchestrator; you control the time loop and pipeline ordering.
      • DNS parameterization assumes applicability of Ayala et al. (2008) fits; verify for extreme regimes.

      FAQ

      Section titled “FAQ”

      How do I choose between turbulent shear and turbulent DNS?

      Section titled “How do I choose between turbulent shear and turbulent DNS?”

      Use turbulent shear (TurbulentShearCoagulationStrategy) for Saffman–Turner regimes with moderate dissipation and when Reynolds lambda is not specified. Use turbulent DNS (TurbulentDNSCoagulationStrategy) when you have DNS-fit parameters (reynolds_lambda, relative_velocity) or want higher-Re effects.

      Can I mix charged and turbulent effects?

      Section titled “Can I mix charged and turbulent effects?”

      Yes. Build charged and turbulent strategies with the same distribution_type, then sum them via CombineCoagulationStrategy (or factory strategy_type="combine") to add their kernels.

      How does particle-resolved stepping differ from discrete bins?

      Section titled “How does particle-resolved stepping differ from discrete bins?”

      Particle-resolved mode bins a kernel radius grid, draws collision pairs stochastically, and calls collide_pairs; discrete/continuous modes apply gain/loss rates directly to concentrations.

      Dispersion and dielectric polarization

      Section titled “Dispersion and dielectric polarization”

      Select van_der_waals in the coagulation factory or construct VanDerWaalsCoagulationStrategy(distribution_type, hamaker_constant, relative_permittivity). The constant is in joules for the material pair across air. The second parameter is the common static relative permittivity. The strategy uses signed numbers of elementary charges from the native state. It supplies one complete thermal collision rate. Supported companions are differential settling and turbulent shear. Adding another Brownian law duplicates the thermal encounter and raises an error.

      Discrete bins and radius PDFs retain their existing fixed composition and prescribed charge per bin. For evolving charge distributions, resolved collisions use actual slot pairs and merge their signed charges. The CPU resolved path computes a dense pair matrix for exact bin bounds. It checks the capture domain for every pair of distinct active slots, including slots with identical material properties. To inspect that matrix for an active population, pass exclude_self_pairs=True to the strategy’s kernel. The CUDA resolved sampler uses tiled pair scans and equal positive counts per box.
