    Nucleation Strategy System

    Complete direct-process context

    Section titled “Complete direct-process context”

    The direct nucleation boundary is shown last in the illustrative explicit-transfer sequence. Its direct-process validation evidence and example regression do not turn the example into a public coordinator, GPU Runnable, backend selector, resident loop, or CPU fallback.

    Convert partitioning precursor gas into fixed-capacity particle slots with a public, conservation-accounted CPU runnable.

    The CPU-only nucleation runnable executes each resolved box independently through the shared transactional driver. It combines immutable potential-rate construction (public construction) with the public Nucleation runnable (runnable execution). It is not a GPU process, scheduler, or general empirical new-particle-formation model.

    Public API, equations, and units

    Section titled “Public API, equations, and units”

    Use public process imports and the concrete species-map configuration. EnvironmentData supplies each box’s thermodynamic input; ExhaustionControls selects fixed-capacity recovery behavior.

    Getting started

    Section titled “Getting started”

    Use the supported CPU example as the runnable starting point. It constructs native Aerosol, unified GasData with precursor and inert lanes, fixed resolved particle capacity, aligned EnvironmentData, and the public NucleationCommitConfig. Its commit controls use ExhaustionControls() and per-box float64 requested_scale, minimum_scale, and minimum_volume sidecars (one element in this example). Do not replace that setup with imports from nucleation.particle_source.

    Execution, fixed capacity, and accounting

    Section titled “Execution, fixed capacity, and accounting”

    The runnable retains the native aggregate and its containers by identity. It supports resolved batches with fixed-capacity slots in each box. The shared driver slices exhaustion controls and stages volume changes per box. A failed box rejects the entire current substep. Full ordered gas names and explicit gas-to-particle pairs define the source mapping; gas and particle widths may differ. Every positive injection lane must be mapped and partitioning-enabled; other gas lanes remain unchanged. It does not resize or compact slots. It divides the duration into equal sequential substeps and re-reads current gas after each successful substep:

    Demand planning is nonmutating. Source transaction rejects invalid preflight atomically. Runnable execution makes each attempted substep a transaction, but is not whole-call atomic: earlier successful substeps remain if a later substep fails. Zero-duration and zero-admitted-demand paths are no-ops after their applicable validation. Nucleation.execute() returns the mutated Aerosol; it does not return demand planning/source transaction diagnostic records. The concrete-only demand planning/source transaction transaction diagnostics include potential, admitted, gas-limited, represented, and reduced events; limiting species; requested, activated, and released slots; policy/scale; gas mass removed; and conservation residual. Particle inventory is concentration-weighted. Per-box/per-species particle-plus-gas conservation uses rtol=1e-12, atol=1e-30.

    The source relies on fixed-slot activation and slot exhaustion policy resolution. Demand is never silently truncated. On exhaustion, enabled resampling is considered first and representative-volume scaling is its fallback; if neither can represent the requested demand, the attempt raises rather than silently discarding it. Native representative-volume scaling scales counts and volume together, preserving pre-existing particle density and gas concentration. It differs from physical volume evolution. The added source is accounted against that scaled extensive inventory. CPU admitted event density is multiplied by current volume; maximum_slot_weight bounds represented counts per new slot.

    Scope, dependencies, and example

    Section titled “Scope, dependencies, and example”

    This contract does not claim universal empirical validity, implicit survival or growth correction, full Vehkamäki physics, GPU execution, dynamic slots, automatic scheduling, hidden CPU/GPU transfer or fallback, or performance. The survival relation is an explicit caller factor, not an implicit Kerminen—Kulmala calculation.

    See Fixed-Capacity Slot Exhaustion Primitives, the equations, and the supported CPU example.

    Direct-Warp low-level step

    Section titled “Direct-Warp low-level step”

    Direct GPU nucleation ships a bounded direct-Warp nucleation step. Import only its supported low-level entry point:

    NucleationConfig, demand planning/capacity staging records, exhaustion resolution controls, NucleationScratchBuffers, NucleationFinalizedDemandBuffers, NucleationDiagnosticBuffers, NucleationExhaustionBuffers, and helpers are concrete-only imports from particula.gpu.kernels.nucleation. Nested ResamplingBuffers is concrete-only in particula.gpu.kernels.exhaustion. They are deliberately not package exports. The CPU-only Nucleation runnable remains the supported high-level CPU process; it is not a GPU fallback.

    Callers explicitly convert ParticleData, GasData, and EnvironmentData, place arrays on one Warp device, and call wp.synchronize() before host inspection. Fixed schemas use B boxes, N particle slots, and S species: particle masses are (B, N, S), particle concentration/charge are (B, N), gas concentration is (B, Sg), partitioning is (B, Sg), and temperature is (B,). Native particle width Sp may differ from full gas width Sg. Direct and prepared calls require explicitly tagged resolved inputs and reject untagged, discrete, and continuous-PDF metadata before particle-array access. Each call requires a NucleationSpeciesBinding prepared with prepare_nucleation_species_map from particula.gpu.nucleation_species_mapping, using preserved full gas names and the explicit source map. Preparation binds the exact transferred arrays; replacement or restart needs fresh preparation. The direct GPU path uses integral int32 event counts and one unit-count slot per event; it does not implement the CPU weighted-slot packing scheme. Sidecars are caller-owned, same-device, contiguous wp.float64 or wp.int32 arrays with documented (B,), (B, N), (B, S), and (B, N, S) schemas. Full-gas demand/transfer sidecars use gas width; resampling scratch uses particle width. Exhaustion resolution owns nested slot exhaustion resampling/scaling sidecars; see fixed-slot exhaustion for their fields. Preflight and phase handoffs may perform bounded aggregate device-status readbacks for validation; these are not CPU state transfers or a fallback.

    Input validation performs read-only preflight, demand planning admits one inventory-limited demand, capacity staging stages counts/free-slot prefixes, and exhaustion resolution uses fully viable resampling before representative-volume-scaling fallback. Commit fuses selected-slot activation and gas transfer. Free-index tails are -1; demand is never silently truncated. A valid configured gate, no-admission, or zero-work result is a successful no-op, not an error or hidden recovery.

    Invalid input rejected before volume scaling primitive entry preserves particle/gas state. Resampling—volume scaling can write documented sidecars before a later rejection. Once slot exhaustion is entered, or a policy integration writer launches, rollback is not promised. Success returns the identical particle and gas containers.

    This boundary excludes hidden CPU↔Warp state transfer, CPU fallback, resize/compaction, GPU Runnable, scheduler/backend selection, direct-process integration orchestration, expanded physics, graph capture, autodiff, and performance guarantees. Fixed-slot management fixed-slot activation, slot exhaustion primitives, and CPU nucleation are dependencies; direct-process integration is only a downstream explicit-transfer integration consumer. See the equations, direct example, and GPU roadmap.
